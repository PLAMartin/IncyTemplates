# 0052 — Customer auth + account shell

## Status
Accepted

## Context

Third piece of commerce/accounts, chosen after Stripe checkout (`0051`): customer-facing magic-link sign-in and a basic `/account` area, closing the gap that slice explicitly flagged — post-purchase download access was purely `session_id`-driven with no way to revisit a purchase later.

Research confirmed this was almost entirely greenfield (no customer session helper, no `/account/*` routes, no account-linking logic anywhere), but the pieces it depends on were unusually well-prepared: new `auth.users` rows already default to `it_profiles.role = 'customer'` automatically via the existing `handle_new_auth_user()` trigger, `it_customers`/`it_entitlements` already carry nullable `profile_id` columns with RLS already scoped to `profile_id = auth.uid()`, and the existing staff `requestMagicLink`/`MagicLinkForm` were already ~95% generic. Spec §18.2's account-linking flow (find an unlinked `it_customers` row by email, set `profile_id`, populate entitlements, record an audit event) had no implementation anywhere, confirmed by grep, not assumed.

## Decisions

**A new `security definer`, parameterless `it_link_customer_to_profile()` function**, not a service-role-only RPC like `it_grant_entitlement`. It reads `auth.uid()` internally rather than accepting an explicit `profile_id` argument, which is what makes it safe to `grant execute ... to authenticated` directly — a caller can only ever link records to their own verified session, never anyone else's. Idempotent (a customer with nothing unlinked is a no-op), so it's called on every successful sign-in via `src/app/auth/callback/route.ts` — the real PKCE production path — not just the first.

**`/auth/callback/implicit` was deliberately left untouched.** It's an explicitly test-only tool (minting a session via `supabase.auth.admin.generateLink()` for authenticated e2e/verification scripts, since that API can only produce implicit-flow tokens, never a PKCE `?code=`) — not part of the real customer sign-in flow, so it doesn't call the linking RPC. Verified live (see Verification below): a session established via the implicit path genuinely does *not* trigger linking, exactly as designed, while the RPC itself works correctly when called with a real session regardless of how that session was established.

**`MagicLinkForm` was genericized in place, not forked.** Added two optional props — `submitAction` (defaults to the staff `requestMagicLink`) and `footnote` (defaults to the existing "Staff accounts only" copy) — rather than duplicating the component. The staff `/sign-in` page passes neither prop, so its behavior is provably unchanged; `/account/sign-in` passes `requestCustomerMagicLink` and different footnote copy. The two server actions differ in exactly two lines: `shouldCreateUser` (`false` for staff, `true` for customers) and the default redirect (`/admin` vs `/account`).

**A separate `customer-dal.ts`, not a modification of `dal.ts`.** `requireCustomerSession()` is deliberately role-agnostic — any signed-in user, staff included, can use `/account` to see whatever purchases are linked to their own profile. `it_profiles.role` is irrelevant to what `/account` shows; unlike the staff DAL, there is no "is this the right kind of account" check, only "is anyone signed in at all."

**`/account/library` and `/account/orders` read via the ordinary session-bound client, not service-role.** RLS already scopes both to `profile_id = auth.uid()` (directly, or joined through `it_customers`/`it_orders`), so no bypass is needed — confirmed live with a real session (see Verification). The library query joins `it_entitlements` to `it_order_items` via `!source_order_item_id` for the product name, deliberately never to `it_products` directly: that table's own migration comment warns against it for historical display copy, and a since-unpublished product would otherwise silently vanish from a live join.

**Real bug caught by live testing, fixed before merging: a route-group restructure.** The first cut nested `/account/sign-in` directly under `src/app/account/layout.tsx`, so the layout's own `requireCustomerSession()` gate wrapped the sign-in page too — an unauthenticated visit produced `/account` → `/account/sign-in?redirectTo=...` → gate fires again on the sign-in page itself → infinite redirect loop, confirmed via `ERR_TOO_MANY_REDIRECTS` in a live Playwright run. Fixed by moving the gated routes (`layout.tsx`, `page.tsx`, `library/`, `orders/`) into a `(protected)` route group — invisible in the URL, so `/account`, `/account/library`, `/account/orders` are unchanged, while `/account/sign-in` now sits outside the group and is genuinely ungated. This is exactly the class of bug that never surfaces in typecheck/lint/build/unit-tests, only in a real authenticated browser session — the reason this pass included two live verification scripts rather than stopping at static checks.

**Header "Sign in" link (both `SiteHeader` and `MobileNav`) now points to `/account`, not the staff `/sign-in` page.** `SiteHeader` itself stays a static, non-session-aware component — deliberately not adding a live signed-in/signed-out check, since that would force every marketing page (homepage, journey, product-family pages) off static/cached rendering per spec §12.4's rendering strategy, a real architectural cost not worth taking for this slice. Staff continue to reach their sign-in page via `/admin`'s own existing redirect (`requireStaffSession()` → `/sign-in`), unaffected by this change.

## Verification

Two live scripts against the real linked Supabase project (throwaway fixtures, cleaned up after each run — same technique as `0047`/`0048`/`0051`):

1. **`it_link_customer_to_profile()` directly, with a genuine authenticated session** (minted via `admin.generateLink()` + following the redirect's fragment tokens directly in Node, then `setSession()` on a fresh anon-key client — no browser needed for this one). Seeded an unlinked `it_customers` + `it_entitlements` row, called the RPC as that session, confirmed both rows' `profile_id` updated to the real `auth.uid()`, confirmed exactly one audit log row, and confirmed the exact query shape `/account/library` uses (session-bound client, RLS, no service-role) correctly returns the newly-linked entitlement. All passed.
2. **The `/account` UI in a real Playwright browser session** (via the implicit-callback test path). Confirmed: the redirect-loop bug (above) before the fix, confirmed fixed after it; the orders empty state renders correctly; sign-out clears the session and returns to `/`; a post-sign-out visit to `/account` redirects cleanly, once, to `/account/sign-in`. The library page correctly showed *no* linked entitlement in this run — expected, not a bug, since the implicit path deliberately skips the linking RPC (see Decisions above).

Also: `npm run typecheck`/`lint`/`test` (450 tests, including a new unit test for `requestCustomerMagicLink` covering the `shouldCreateUser`/redirect differences from the staff action) and `npm run build` all pass. An authored-only pgTAP test (`supabase/tests/it_link_customer_to_profile_test.sql`, per this repo's established "not run in this environment, no Docker" convention) covers the same linking/idempotency/anon-cannot-call behavior at the SQL level.

## Follow-up

- **No signed-in state in the header.** Deliberately deferred (see Decisions) — would need a client-side session check or a different architecture to avoid making every marketing page dynamic.
- **No checkout → account integration yet.** A signed-in customer's `/account/library` shows only entitlements already linked to their profile; the checkout flow itself (`0051`) still doesn't prompt sign-in or pre-fill anything — a guest buyer only gets access via their `session_id`-driven success-page download until they separately sign in with the matching email and the linking RPC catches up.
- **No password/account settings, no email-change flow.** Spec §18.3's email-change handling is unimplemented — out of scope for this slice.
- **Real end-to-end verification of the actual production PKCE path** (a genuine `signInWithOtp()` browser call, receiving a real email, clicking through) wasn't performed — Resend still isn't wired and this project's default Supabase email sender has a known low rate limit (per prior project memory). The RPC itself is proven live and correct (Verification, item 1); only the exact email-click journey through `/auth/callback` (not `/auth/callback/implicit`) remains unverified end-to-end, though the code path is a two-line, type-checked addition to an already-working route.
