# 0012 — Free templates: view on-site instead of download

## Status
Accepted

## Context
Free templates were originally delivered via `POST /api/downloads/free`,
which emailed the visitor nothing but returned a Supabase Storage signed
URL that triggered a browser file download (`docs/decisions/0011-...md`
covers the abuse-protection scope for that endpoint). The product
direction changed: visitors should view the template content on the site
itself rather than download a file. This only affects the free-template
flow — paid products still show `WaitlistForm`, untouched.

Free-template files are markdown worksheets (confirmed: every
`access_type: "free"` product's `template`-role file is
`file_format: "markdown"` in `content/seed/catalogue.ts`), so "view on the
site" means server-rendering that markdown, reusing the same
`next-mdx-remote/rsc` + `rehype-slug` pipeline the guides feature already
uses (`src/app/(marketing)/guides/[slug]/page.tsx`).

## Decision

**Cookie-based view grant instead of a signed URL.** `POST
/api/templates/view` (replacing `/api/downloads/free`) keeps the same
email-capture, same-origin check, rate limiting
(`src/server/downloads/rate-limit.ts`), and audit logging as before, but
instead of returning a signed storage URL it mints a signed, HttpOnly
cookie (`src/server/downloads/view-grant.ts`) scoped to the specific
`productId`+`fileId` with a 1-hour TTL, named per-product
(`it_view_grant_${productId}`) so viewing several free templates in one
session doesn't clobber earlier grants. `src/app/(marketing)/templates/
[slug]/view/page.tsx` verifies the grant server-side, re-resolves the file
(in case the product was unpublished in the gap between submit and view),
downloads it from the private `it-free-files` bucket, and compiles it with
`compileMDX` (called directly, not the `<MDXRemote source .../>` JSX form
guides use — that form defers the async compile into React's render
machinery in a way a wrapping `try/catch` cannot catch, and this app has
no `error.tsx` boundary, so a malformed file would otherwise crash to
Next's raw error page instead of a friendly fallback).

A 1-hour TTL is more generous than the old link's 300-second TTL
intentionally: the old TTL bounded how long a *shareable* signed URL
stayed valid, while this grant lives in a non-shareable HttpOnly cookie —
the relevant risk it bounds is a stale browser tab, not link sharing.

**`DOWNLOAD_HASH_SECRET` is now a hard requirement for this route, not
optional defense-in-depth.** Decision 0011 treats it as skippable (the
per-IP rate-limit check just logs a warning and continues without it)
because it was only ever a secondary signal on top of the primary control
(the signed URL itself, generated by Supabase using its own key). For the
view grant, the HMAC signature *is* the entire access-control mechanism —
`productId`/`fileId` are not secret, they're in the page HTML. If the
secret were unset and minting silently produced an unsigned or
guessable cookie, anyone could hand-craft a valid grant for any free
product without ever submitting the form. `POST /api/templates/view`
therefore 503s if `DOWNLOAD_HASH_SECRET` is unset, and
`mintViewGrant()` throws rather than degrading.

**No new markdown-sanitization step (deferred).** MDX compiles
`<tag>...</tag>`-shaped content into real DOM elements, not just escaped
text — a genuine stored-XSS surface if template content ever contained
something like a crafted `<img onerror=...>`. Today, free-template
content is added the same way guides content is: committed to the repo /
seeded, with no admin upload UI yet. That's the same trust boundary
guides already operate at without sanitization. Decision: accept this as
equivalent to any CMS's rich-text pipeline for now, and revisit
(`rehype-sanitize` or a tag/attribute allowlist) when an admin upload UI
ships and the trust boundary actually changes.

**`it_free_download_requests` / `it_download_events` tables are reused
unchanged**, no migration. Neither table has an event-kind column — both
are already generic "requested/accessed this file" audit logs. The
`source` field passed into both inserts gets a `-view` suffix (e.g.
`product-page-view`) so old download-era rows and new view-era rows can
still be told apart in analytics by string, without a schema change.

**Non-markdown template files are guarded against, not assumed away.**
`FileFormat` includes `pdf`, `docx`, `xlsx`, etc., and nothing in the
schema stops a future free product's `template` file from being
non-markdown. The view page checks `file_format === "markdown"` and shows
a "can't view this online yet" fallback otherwise, rather than attempting
to render arbitrary bytes as MDX.
